# User Guide

Switch roles from **Viewing as** in the top bar. Each role sees the same applications; what each can *do* differs.

## Riya — Associate

1. **Intake.** Applications → New intake. Drop the week's decks and forms (or paste text) → *Receive & process*. Read the intake result: readable files, failed files with the reason, duplicates skipped.
2. **Extraction review.** Application → Documents. Check each extracted field against its page (*View text*). *Confirm* correct values. *Edit* wrong ones; the original is kept. Missing fields stay blank and are never guessed.
3. **Evidence and research.** Application → Research & evidence. Work the high-priority tasks. *Update* a task with findings and the sources you actually opened. If a source was unreachable, mark it *inaccessible* and say why. *Log evidence* with its source type (tier 1–7), URL, date, excerpt and the claims it supports or contradicts. Two independent supporting sources make a claim *corroborated*.
4. **Conflicts.** Overview → Conflicting claims → *Review*. Record what the founder or a source said. The platform never picks a side.
5. **Scores.** Evaluation → *Correct* on any criterion. Give a one-line reason, a category, and whether the correction is case-specific or reusable. Reusable corrections become proposed learning rules.
6. **Hand-off.** *Send to partner review*.
7. **Scheduling.** After Kushal approves a call, Scheduling shows three proposed Tue/Thu 30-minute slots. *Confirm* one (confirmed by hand, not a calendar booking) and download the `.ics`.

## Aditya — Partner

- Deeptech applications (e.g. Pumpwise) are flagged "Aditya", and he is added to their calls automatically.
- Review technical feasibility in Evaluation → Product & tech and Path to market (certification and milestone unknowns). Add comments and corrections.
- Approve or reject proposed learning rules (Learning & Feedback).
- Documents for non-deeptech applications are restricted for this role.

## Kushal — Principal

- **Decision room** lists every applicant with the recommendation, decision status and whether he has opened it. A decision can only be recorded after he opens the application.
- Choose *Approve call*, *Request information*, *Hold* or *Pass* (pass needs a reason), and write a rationale. Approving a call auto-proposes slots.
- *Reopen* a decided application to start a new cycle. History is kept.
- Approve rubric versions (Thesis & Scoring), learning rules, and the portfolio dataset verification.
- Review possible portfolio overlaps: *Confirm conflict* or *False alarm*, with a note.

## Reading a scorecard

- **Score 1–5** per criterion, or **n/a** when evidence is insufficient (unknown is not zero).
- **Evidence state:** strong / mixed / weak / insufficient / conflicting.
- **Confidence** stays at medium or low until independent evidence exists. Nothing is auto-verified.
- Each signal shows its effect (+0.5, −1, …) and a source chip (e.g. `Form p2`) pointing to the stored page.
- **Stated vs revealed thesis** are shown separately. RP-9 (drift) is shown but never scored.

## Backtesting

Two tabs. *Retrospective* reads the memo text (without the decision paragraph). *Approximate point-in-time* reads only application-time facts. Read the in-sample warning and the stage-label artefact before quoting any agreement number.

## Administration

Provider status, AI-failure drill, permission matrix, job queue, audit log, JSON export/import, reset to the case batch or to empty.
